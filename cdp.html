Customer Data Platform An existing product that had to become legible

I joined a customer data platform mid-build: the screens existed, but no system coordinated how anything looked or behaved. Over four months I audited what was there, designed the system it was missing, and specified the screens built on it — down to their error and edge states — before handoff.

Challenge

The product was well into its build with no shared system: every screen answered the same design questions its own way, and the rules holding it together lived in people's memory, not on screen.

Solution

Name the parts before touching any screen — one language for color, type, and behavior — then rebuild the riskiest flows on top of it, with every state designed before handoff.

Outcome

In development — design system and screen specs handed to the dev team. No launch or usage numbers yet: this page shows the work, not its results.

The situation

The pieces existed. The rules connecting them didn't.

A CDP for marketing teams in Thai enterprise and SME businesses — segments, imports, journeys, RFM scoring, PDPA consent, 20+ areas, zero rebuild budget, legacy schemas untouchable. Its rules lived in people's memory, not on screen:

  • Setup dependencies — what had to be configured before a workflow opened. Import didn't know Identity Data had to come first, so nothing stopped data from entering before the rules that match it to a customer existed.
  • Data states — upload, mapping, error, and confirmation looked like the same screen, so nothing caught a mistake at the moment it happened.
  • Campaign logic — journey triggers and RFM groups got rebuilt bespoke per feature, so a new campaign type meant a new one-off screen instead of a reused rule.
  • Handoff names — Dev, PM, and QA each described the same screen differently, and every gap between those descriptions cost a round of back-and-forth before dev could build it right.

The absence of a system doesn't look like a problem on any single screen — each screen looks fine on its own. The cost lives between screens: the same design question answered five slightly different ways, no visible rule saying which answer is the intended one, nothing for QA to test against. A rule that isn't visible doesn't disappear — it moves downstream, and gets more expensive the longer it stays hidden. Every plate below is one of those rules, made visible.

Decision 01 · Create shared language

A shared language starts smaller than a screen.

With no shared vocabulary, each screen invented its own colors, sizes, and buttons — drift that would only compound as more areas got built. So the first rule: no feature screen gets redesigned until the parts have names. Color in three ramps, type in six levels, buttons in five variants — small enough to memorize, complete enough to build any screen in the product. Once design, dev, PM, and QA had one name for each part, every plate after this one could assume the vocabulary instead of re-explaining it.

The patterns every area borrowed.

Two problems shared one shape: twenty-plus areas each needed wayfinding and progress, and the costliest path in the product was importing data before hard_id and soft_id were configured — data entering without the rules that match it to a customer. Two rules answered both. Navigation reads as the marketer's mental model, not a menu: Data Manager, PDPA, Campaign, Analytics, Settings. And one tracker pattern serves two duties — onboarding, and the Identity Data setup gate: Import and Export stay locked until identity is configured, with gated empty states redirecting users to setup.

The complex parts became components too.

Journey automation and RFM (recency–frequency–monetary) scoring are where a design system usually gives up and lets every screen go bespoke — which is exactly how those screens become unreadable again. The rule held instead: even the complex parts are components. 12 node types across trigger, action, operator, and campaign, bound by one strict completeness rule — written to be testable, not implied — plus an RFM set covering the scoring donut, seven customer groups, and the status-tag states.

The risk that remains

The system validates configuration, not outcome. A campaign whose segment logic resolves to zero people would pass every gate and go out to nobody — a silent failure no component would catch. I'd add a reach-validation layer that warns before send.

What I'd verify next time

The four-step gate and 2–3 levels of nesting were judgment calls, made without usage data to confirm either — the product hasn't launched, so that data doesn't exist yet. The system makes revising cheap — but cheap to revise is not the same as right. Instrumentation after launch would say which judgment to revisit first.
